# Spike 1B 阶段 2（Sonnet 5）报告

- 协议：v1.1（冻结 commit `0a96a96`；预算计划 `4c31c06`）。分数冻结在 `2524988`（`1b-stage2-sonnet5.json`），冻结时还没有查看任何 transcript。
- 模型：`claude-sonnet-5`，effort `high`（API 返回的模型标识与此一致）；Claude Code 2.1.280；`apiKeySource: none`（订阅登录）。
- 规模：160 个 slot（8 个 hypothesis × 4 个条件 × 5 次，含 gate），全部 `VALID completed`。没有重跑，没有被预算截掉，没有单次超支。按 API 标价折算共 $55.72。

## 预注册判定：1B 不通过（证据完整率触发终止条件），且一项 harness 不变量不为 0

| 门槛（§3.7） | 通过 | 终止 | 结果 | |
|---|---|---|---|---|
| harness 不变量 | 0 | > 0 先修 harness | `harness_errors = 1` | ✗ |
| forward 归因正确率 | ≥ 80% | < 50% | 100% | ✓ |
| 每个真 hypothesis 的 forward 正确率 | ≥ 60% | 任一为 0% | 5 个真 hypothesis 全部 100% | ✓ |
| **证据完整且归因正确率** | ≥ 60% | < 40%（且归因 ≥ 80%） | **25%**（归因 98.1%） | **✗ 终止** |
| 负对照假 SUPPORTED 率 | ≤ 10% | > 25% | 0% | ✓ |
| swap 镜像一致性 | ≥ 80% | < 60% | 97.8% | ✓ |
| identity 不一致率 | ≤ 10% | > 25% | 3.7% | ✓ |
| 系统性 revision 混淆 | 0 个 fixture | ≥ 2 个 | 0（最高的 fixture 也只有 11/40） | ✓ |

按决策矩阵，「归因正确率达标，但证据完整率很低」要按 **1B 不通过** 处理。本报告不修改这个判定，v1.1 的数据永久冻结为失败实验：不重新评分，不补跑，也不替换出过 harness 错误的那个 slot。

**这个判定能说明的范围**：在 v1.1 协议下，模型没有达到预注册的证据完整性要求。预注册给这种失败配的机制解释是「agent 根据 diff 形状猜结论」，但下面的事后分析显示，同一批数据并不支持这个解释。判定规则照常执行，只是这条解释被数据削弱了。

**harness 不变量**：唯一的一次是 filebrowser H2/identity_base/r3。agent 给 `search_code` 传了一个 `git grep -E` 无法解析的正则，harness 把它归成了 `git_error`，返回给 agent 的信息是含糊的「repository read failed」。正确的做法是把它当作输入错误，返回「无效的正则」。这是错误分类和提示信息的缺陷，不会损坏数据，影响范围只有 1 次工具调用，这个 run 的归因也是正确的。继续做任何实验之前都要先修掉（升为 v1.2）。

## 事后分析（未预注册，不改变上面的判定）

### 1. 失分几乎全部来自路径事实

| fixture | 翻转事实被引用 | 路径事实被引用 | 路径事实所在代码被工具返回过（agent 看到过） |
|---|---|---|---|
| Authlib | 97% | 39% | 85% |
| Caddy | 90% | **0%** | 65% |
| File Browser | 97% | 46% | 99% |

有 102 个 run，唯一没有满足「证据完整」的原因就是缺少路径事实。agent 基本都引用了翻转点，而且引用在正确的 revision 上；但从入口到翻转点的连接代码，它们看过却很少引用。在 Caddy 上，agent 引用了 2xx 匹配器（约 29/40 个 run）和运行时执行 handle_response 路由的 `reverseproxy.go:958`，却几乎从不引用挂载那两行（`goodResponseHandler.Routes = append(...)`、`rpHandler.HandleResponse = append(...)`）。不少陈述其实**用文字把路径讲清楚了**，例如「路由只被加进 goodResponseHandler，该 handler 匹配 2xx，并挂在 rpHandler.HandleResponse 上」，但没有引用对应的行。

### 2. 预注册里「在猜」这个解释，和其他预注册指标相矛盾

终止条件把「归因高、证据完整率低」解释为 agent 在根据 diff 形状猜结论。但同一批数据里：

- 翻转事实的引用率是 90–97%；
- forward 条件下 5 个真 hypothesis 全部 100% 正确；
- 负对照假 SUPPORTED 为 0；
- 专门用来识破「看 diff 形状猜」的 S3 H3 陷阱，20 次里答对 19 次；
- swap 镜像一致性 97.8%。

这些结果更符合另一种解释：**agent 知道路径，只是没有把路径引用下来**。

### 3. 可能的协议层原因（假设，需要新实验来检验）

- prompt 要求 agent 用 `quote` 把引用缩小到最关键的几行，这会促使 agent 只引用翻转点那一行。而 golden 要求每一跳单独引用。在 File Browser 上，路径所在的代码有 99% 被工具返回过，引用率却只有 46%。这个差距和上面的解释一致。
- 另一个原因可能是 agent 用运行时代码来论证路径（Caddy 的 `reverseproxy.go`），而 golden 要求的是配置构造代码。

### 4. 修订 golden 能不能改变判定：不能

Caddy 那种「运行时」证据缺少关键的挂载一环，不满足 §3.4「同样充分」的标准，所以不修订 golden。退一步说，即使把 Caddy 的路径事实全部豁免，证据完整率也只有 45%（仍低于 60%）；只有把所有路径事实都豁免才能到 89%，而那等于取消这条评分规则本身。**判定不取决于修订怎么做。**

### 5. 其他发现

- **3 个 run 归因错误**：2 个是某一侧的观察没有记完整（INCOMPLETE），结果是 UNATTRIBUTED，和阶段 1 的漏记同属一类；1 个是 S3 H3 在 swapped 条件下落入陷阱，把修复那一侧判成「Windows 越界被修掉了」。
- **identity 措辞筛查**：除 "remov*" 之外有 23 条陈述被标出。其中 16 条是在正确地说明「两侧代码没有变化」，4 条在描述代码结构（「加到 X 上」），3 条在描述字符串变换。杜撰两侧差异的一条都没有。
- **引用错误**：尝试阶段的引用错误率是 11.9%；12.5% 的 run 尝试过跨 revision 引用，都被拒绝后自行改正了。

## 后续（经 Codex 复核）
